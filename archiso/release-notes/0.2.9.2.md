A point release about one thing: the security features were checked instead of
described, and checking them found what reading them had not.

Three of the four things fixed here were not visible in the code. A firewall
that had been running for weeks while its own status command said it was not
there. A synguard policy that had never once acted. A daemon that took the
caller's identity from the caller. And one rule that turned a working laptop
into a machine that could not run `rm` — found by running it, on real hardware,
which is the only way it was ever going to be found.

23 commits. Nothing in this release is a new feature you asked for; most of it
is a thing that was already claimed being made true.

## The firewall was always on and said it was not

SynapseOS has carried a default-drop input firewall for a while. `synnet`
applies it at every start: loopback, replies to connections you made, ICMP and
ICMPv6, anything from the local network, DHCP — everything else dropped.

`synnet --status` reported *"no synnet table loaded — daemon has not run"*
anyway. Listing an nftables object needs `CAP_NET_ADMIN`, so as an ordinary
user that call always failed, and the old status read any failure as absence. A
fully firewalled machine denied its own firewall to whoever asked. It never
mentioned the input firewall at all either — only the egress blocklist — so even
under `sudo` the thing you would run it to ask was missing from the answer.

It now makes three claims and keeps them apart, because *what synnet believes*
and *what the kernel holds* are different statements and conflating them is how
this happened: what was **asserted** (published to `/run/synnet/firewall.state`,
world-readable, which is what makes an unprivileged answer possible at all),
what the **kernel** holds (only when it can look — and it says so plainly when
it cannot, rather than turning "not allowed" into "not there"), and the
blocklist.

**And "self-heals a manual `nft flush`" was a comment, not a behaviour.** The
chain was built once at start; a flush from anything took it away until the next
daemon restart, with the journal still showing the firewall coming up — because
it had, once. The monitor loop re-checks once a minute now and rebuilds, logging
a running count, because *"this happened at boot"* and *"this has happened forty
times today"* are different problems.

### It is in Settings now

**Settings ▸ Network** reports the preference, the state and the service
separately, plus a row that appears only when the firewall has actually been
rebuilt — something flushing nftables is worth knowing about. There is an on/off
switch, and the labels say what happens rather than what the switch is called:
*"answer anything that reaches this machine, on any network"*.

Off had to be **remembered**, not just applied. The daemon rebuilds a missing
chain once a minute, so a switch that only deleted the chain would flip itself
back inside sixty seconds — the guard undoing the user instead of the flush it
exists for. `synnet --firewall on|off` writes the preference and the daemon
re-reads it every tick. An absent, unreadable, empty or malformed preference all
mean **on**; the single string that disarms the machine is the exact word `off`.

## synguard's policy acts now — and the rule that had to break a laptop

SynapseOS shipped 55 synguard rules and **not one of them carried `deny` or
`quarantine`**. The daemon ran with `--mode enforce`, so acting was permitted;
nothing loaded ever asked for it. It detected, it alerted, and it had never
stopped anything — which also means its acting path had never run on a real
machine.

`50-default-deny.rules` arms three. The bar was not *"is this suspicious"* but
*"does anything on a working desktop do this, **ever**"* — plus "if it fires
wrongly, is the cost recoverable", because a false positive costs a **process
tree**.

- **`/etc/ld.so.preload`** — the classic userland-rootkit hook. No Arch package
  manages that file.
- **A canary** — the positive control. A rule that never fires is
  indistinguishable from a rule that is not working, and every other rule here
  is one you hope never fires.
- **Execution out of the top of `/dev`** — quarantined rather than killed, so
  the process survives to be looked at.

What was left out is written into the file with the reason, because that is
worth more than a shorter file. **Denying unexpected module loads would break
this distribution**: every DKMS rebuild and NVIDIA driver update loads modules
from programs not on the allow-list, and `synapse_kmod` is itself DKMS — it
would fire on a routine `pacman -Syu`. **Denying a shell spawned by sshd** is
either inert or a total SSH lockout depending on which login shell the account
has, which the rule cannot see.

### The rule that took a machine down

`deny-ld-preload` shipped matching **any** open of that path, on the reasoning
that refusing the *read* neuters an already-planted rootkit — glibc treats a
failed open as "no preload" and carries on. That is true, and it is true **only
of the kernel path**, which can refuse an open.

The userspace path cannot refuse anything. It sees the open after it has
succeeded, and its only move is to kill the opener's process tree. `ld.so` opens
`/etc/ld.so.preload` on **every exec**. So on a machine where that file existed
and the BPF gate was not armed — which is every machine, because
`--bpf-enforce` is not in the shipped unit — every command on the system had its
tree torn down, including the `rm` you would use to delete the file, and `sshd`.

That is exactly what happened during testing. `access write` now: a read is what
a working system does with that file, a write is what an attack does.

**If a rule ever does lock you out, you do not need to reinstall.** The
procedure is in `50-default-deny.rules` itself:
`systemd.mask=synguard.service` on the kernel line at the boot menu, for that
one boot. Note that `synapse.bpf_enforce=0` is **not** this — it disarms the
kernel gate only, and a userspace deny goes on killing regardless.

### Kernel enforcement, measured

`--bpf-enforce` is still **not** in the shipped unit, and that decision is now
recorded rather than assumed. The gate itself passed everything: the 30-second
warmup declines to act and records why, root is refused on a root-owned file
(something only an LSM can do), a wedged daemon fails open and re-arms when it
recovers. 16 checks, 0 failures, on hardware.

What argues against arming it is what the exercise found on the way there —
including that the thing which broke a machine was a *userspace* rule the gate
had nothing to do with. `tools/bpf-enforce-check.sh` is in the tree; it arms the
gate, watches, and disarms, behind a dead-man timer that puts the machine back
even if the script or your session goes away.

A kernel refusal also used to leave **no trace in the journal** — the counter
was logged once at boot and never again, so a gate that had refused thousands of
opens looked identical to one that had refused none. Refusals are logged when
they happen now, and `SIGUSR1` dumps the full state on demand.

## The AI daemon believed whoever was talking to it

`synapd` took the caller's PID from the caller's own message header —
`w->client_pid = hdr.client_pid` — with `SO_PEERCRED` consulted nowhere. Identity
supplied by the thing being observed, in the daemon whose job is security
telemetry.

Not a privilege escalation: the socket is `0660 root:synapse`, nothing on that
path kills anything, and synguard re-verifies process identity itself before
acting. But the claimed PID reached two places that matter — the rolling context
the model is later shown, and the anomaly log — so attacker-controlled text
could be filed against another process and read back as that process's history.

The kernel decides now, and a header that contradicts it is logged rather than
smoothed over. **No credentials means attribution to nobody, never a fallback to
the claim** — that fallback is the tempting one-liner and it hands the decision
straight back to the sender.

Found by an outside review of the repository. The finding was real and correctly
sized.

## A security policy, and a backlog with definitions of done

`SECURITY.md` is new: how to report a vulnerability privately, what is in scope,
what is not, and which versions get fixes. Two things it says explicitly because
they are specific to what this project is — **the AI is a privilege boundary**,
so a prompt-injection path that turns model output into a privileged action is a
vulnerability here rather than a curiosity; and **anything that makes a security
feature silently inert counts**, even with nothing exploitable yet. This release
is four instances of that second one.

`docs/SECURITY-ROADMAP.md` is the backlog behind it — signed releases,
reproducible builds, a structured `synapse_kmod` pass, a threat model — each with
what "done" means, because a task whose completion is a matter of opinion never
completes. An independent third-party audit is named at the top as deliberately
**excluded** rather than quietly omitted: a one-person alpha cannot buy one, and
listing it would turn the list into a wish.

## The desktop

**Night light did nothing on AMD and Intel laptops.** synui built one 1024-entry
colour transform for every output, on the reasoning that a colour transform is
resampled by whatever consumes it. It is not — the kernel checks the LUT length
against the CRTC's gamma size. 1024 was a guess that happened to match NVIDIA,
so it worked on the development desktop and silently did nothing everywhere
else. The length comes from the hardware now, per output.

**Live wallpapers segfaulted on AMD.** The session exports `MANGOHUD=1` so games
get the overlay without a per-game wrapper — and MangoHud's Vulkan manifest turns
that one variable into "load my layer into every Vulkan client", including the
wallpaper engine, whose mpv asks for a Vulkan hwdec device. It died in MangoHud's
own `vkCreateDevice` hook before painting a frame. NVIDIA picks a different hwdec
and never calls it, so three engines ran happily on the dev desktop while every
AMD laptop got a still picture and a core dump.

**The image viewer did nothing from the application menu**, because `%f` with
nothing selected expands to nothing and the wrapper printed a usage line to a
stderr no launcher reads. It opens its recent-images list now. It also grew a
close button and a chevron at each side — it is a full-screen panel with no
window chrome, so everything it could do was on the keyboard, and a picture
opened by double-clicking a file could not be dismissed by the hand that opened
it.

**Double-click a window border** to fill the screen along that axis — top or
bottom for height, left or right for width, and the axis you did not touch keeps
the size you gave it. A second double-click puts it back. Also
`Super`+`Ctrl`+`Up` / `Super`+`Ctrl`+`Left`.

**Files' right-click menu**: six "Open with …" rows are one row and a submenu.
For an ordinary PNG they were most of the menu's height and carried its longest,
most-elided labels.

**DaVinci Doctor** (`syn resolve gui`, or the menu) — drop the DaVinci Resolve
installer on the window, or point it at one, and it walks the four jobs in the
order they have to happen, including the OpenCL runtime for the GPU you actually
have, which is the step that fails late and blames the graphics card.

## Fresh installs follow their own theme

The installer wrote `glass_level = 55` into every new synuirc. A number is an
explicit answer and an explicit answer survives a theme switch — so all twelve
non-glass themes were handed Prism's level instead of the opacities they were
tuned with, permanently. It was redundant too: synui already gives a glass theme
that same level when nobody has set one.

`glass_level = auto` now. Also `widget_glass = on` rather than `auto`, and the
asymmetry is the point: the desktop widgets are quickshell and cannot ask what
the theme is — they read a file that is only written when somebody *picks* a
theme, and a fresh install *names* one without ever picking it. `auto` left them
solid on a glass desktop.

⚠ **This only affects new installs.** On an existing machine, set those two
lines in `~/.config/synui/synuirc` by hand.

## The updater

`syn-update apply` used to reinstall everything you unticked at install time.
Every SynapseOS package is a checkbox now, so *"not installed"* is an answer —
and the updater could not tell that from *"the tree gained a component"*. It
reads `/etc/synapseos/components.conf` now: named there and absent is your
answer and is kept; absent from the file entirely is genuinely new and still
installs itself. `syn-update apply <name>` is the opt-in, and it is remembered.

It also explains itself when a commit contains nothing installable — a run that
listed two commits and then said "already current" read as an updater refusing
to work, when in fact the commits were documentation and a component that
machine does not have.

## Known issues

- **The false-positive rate of the three armed synguard rules has not been
  measured.** They are chosen to be things nothing on a working desktop does,
  and that is an argument rather than a measurement. If a program of yours is
  killed or frozen unexpectedly, `journalctl -u synguard | grep -E
  'DENY|QUARANTINE'` will name the rule, and moving
  `/etc/synguard/rules.d/50-default-deny.rules` aside plus
  `systemctl reload synguard` turns all three off.
- **Releases are checksummed but not signed.** The `.sha256` proves the file is
  intact, not that it came from us. Signing is item 3 of the security roadmap.
- The live ISO carries **no AI model** by design; `synapd` runs in shell-assist
  mode there and `syn status` reporting "model ✗ not installed" on live media is
  expected. The installer asks which model you want and downloads it onto the
  target.

## Getting the image

The ISO is in two parts — GitHub caps a release asset at 2 GiB — so there is a
join step before there is an ISO. Download **both** `.part` files and
`SynapseOS-0.2.9.2-x86_64.iso.sha256` into one folder. The join is a plain
byte-for-byte concatenation; the checksum is what tells you it worked.

### Linux / macOS

```sh
cat SynapseOS-0.2.9.2-x86_64.iso.part* > SynapseOS-0.2.9.2-x86_64.iso
sha256sum -c SynapseOS-0.2.9.2-x86_64.iso.sha256    # shasum -a 256 -c on macOS
sudo dd if=SynapseOS-0.2.9.2-x86_64.iso of=/dev/sdX bs=4M status=progress oflag=sync
```

Find `/dev/sdX` with `lsblk` first, and write to the **disk** (`/dev/sdb`), not a
partition on it (`/dev/sdb1`).

### Windows

Whoever installs a Linux distro is usually still on the OS they are leaving, so
this path is spelled out rather than assumed away. In **Command Prompt**, in the
folder you downloaded to:

```bat
copy /b SynapseOS-0.2.9.2-x86_64.iso.part00 + SynapseOS-0.2.9.2-x86_64.iso.part01 SynapseOS-0.2.9.2-x86_64.iso
certutil -hashfile SynapseOS-0.2.9.2-x86_64.iso SHA256
```

Both mistakes this invites produce a file that looks finished:

- **`copy` without `/b`.** In text mode it stops at the first `0x1A` byte, a few
  hundred KB into the image. Short file, no error, a stick that will not boot.
- **A wildcard source** (`copy /b *.part* out.iso`). `copy` takes wildcards in
  directory order, which is not guaranteed to be sorted. Name both parts, in
  order, joined by `+`.

So check it. `certutil` prints the hash to compare against the `.sha256` file, or
**PowerShell** will do the comparison and answer `True`:

```powershell
(Get-FileHash -Algorithm SHA256 .\SynapseOS-0.2.9.2-x86_64.iso).Hash -eq (((Get-Content .\SynapseOS-0.2.9.2-x86_64.iso.sha256) -split '\s+')[0]).ToUpper()
```

For reference, the ISO's SHA256 is
`PASTE-THE-SHA256-HERE-AFTER-BUILDING`.

Then write it with **[Rufus](https://rufus.ie/)** — pick the ISO, START, and
choose **DD Image mode** when it asks, because this is a hybrid image and ISO
mode rebuilds boot files it has no reason to get right — or
**[balenaEtcher](https://etcher.balena.io/)** (nothing to configure), or
**[Ventoy](https://www.ventoy.net/)** (copy the `.iso` onto an existing Ventoy
stick and pick it from the menu). **Writing a stick erases it**; Ventoy is the
exception.

Boot it from your firmware's boot menu — usually `F12`, `F11`, `Esc` or `Del` at
power-on. Secure Boot has to be off, or SynapseOS enrolled: see the wiki's
[Secure Boot](https://github.com/velle999/SYNAPSE/wiki/Secure-Boot) page.
