The security release. `synguard` has always been able to *notice* things and
never to stop them — it shipped 55 rules and not one of them could prevent
anything. That changes here, along with a compositor that stopped handing every
application the keys to your screen and keyboard.

## `synguard` can refuse something now

Every previous release detected and reported. A rule could log, alert, or ask
the model — and then the thing it was worried about happened anyway. The only
"enforcement" available was killing the process afterwards, which is a strange
kind of protection: the file has already been read by the time the killer runs.

**There is now a BPF-LSM gate that returns `-EPERM` from inside the kernel**, so
a denied open never opens. It is opt-in — `--bpf-enforce` — because a security
layer that starts refusing things the moment you upgrade is its own kind of
outage.

Everything about it is built to fail open rather than fail closed:

- **A 30-second warmup** after attach, so a boot cannot deadlock behind a policy
  that has not settled.
- **A dead-man heartbeat.** If the daemon stops beating, the kernel side stops
  denying. A wedged `synguard` cannot lock you out of your own machine.
- **A deny budget**, so a rule that matches far more than its author expected
  runs out of rope instead of taking the system with it.
- **Additive only.** The gate can refuse; it can never approve. An `allow` rule
  deliberately compiles to nothing, so nothing here can overrule an AppArmor or
  SELinux verdict that would otherwise have denied.

Rules are compiled down to a form the kernel can actually run, and **a rule that
cannot be expressed exactly is refused by name at startup** rather than silently
approximated. Two engines quietly disagreeing about the same policy file is the
failure this design exists to prevent — a rule that loads, looks armed, and can
never match is worse than one that fails loudly.

`synguard status` will tell you whether the gate is open right now, and if it is
not, which of the conditions above is holding it closed.

## The detector was going blind, and its counters said everything was fine

Several things were wrong at once underneath, all of them invisible from the
outside — which is the property that makes them worth a release note.

**Event bursts lost about 80% of their events.** The reader took one 4 KB read
per 100 ms poll, which caps out around 620 events a second. That is comfortable
at an idle rate of ~46/s and useless under any burst worth detecting: a measured
20,000 events in 51 ms lost 15,930 of them. The ring is bigger, the reader drains
in a loop, and **a lapped ring now raises an alert** instead of being inferred
from a counter nobody was watching.

**A slow model answer blinded the reader completely.** Classification ran inline
on the thread reading the kernel's event feed, so while the AI was thinking,
nothing was being read. In the worst observed case 100 events out of 100 went
unseen — and `--mode audit` looked perfectly healthy throughout, because it skips
the baseline that feeds the classifier. Classification now runs on its own
thread. While auditing that, ThreadSanitizer found three pre-existing races in
the statistics counters; those are now atomic.

**Reading the kernel's event log used to consume it.** Anyone running
`cat /sys/kernel/synapse/syscall_log` to look around stole the events out from
under the daemon — an operational footgun that bit twice during development, and
a way to blind the detector on purpose after a compromise. Every reader has its
own cursor now.

**About 4,900 benign alerts per boot drowned the real ones.** Rules named
`*-write` fired on reads, because the rule language had no way to say otherwise:
one boot produced 4,510 "systemd unit write" alerts of which 4,485 were systemd
reading its own units, and 255 "profile.d write" alerts that were login shells
sourcing `/etc/profile.d`. Rules can now say `access write`, and repeated alerts
collapse into a count instead of scrolling the real one off the screen.

**A kill could land on the wrong process.** By the time a verdict is acted on,
the event is up to a poll interval old and the pid may have been recycled onto
something innocent. That is now checked and refused.

**And enforcement no longer fires on things that never happened.** The kernel's
probes report at syscall *entry*, so an open that failed — no such file, or
permission denied — was indistinguishable from one that succeeded, and the deny
path treated both as an access. It killed process trees over files the kernel had
already refused to open. `openat` now reports at syscall exit with its return
value, and a failed access is detected and logged without anything being killed.

## Any application could read your screen and your keystrokes

`synui` handed out the privileged Wayland protocols to anyone who asked. No
gating of any kind:

    zwlr_screencopy_manager_v1        read the whole screen, continuously
    zwp_input_method_manager_v2       see everything typed
    zwp_virtual_keyboard_manager_v1   inject keystrokes
    zwlr_data_control_manager_v1      watch every clipboard change
    zwlr_foreign_toplevel_manager_v1  enumerate, focus and close other windows
    zwlr_gamma_control_manager_v1     repaint or blank the display

Any client — a Flatpak, a game, anything you ran once out of a tarball — could
bind these and start recording.

**`wp_security_context_v1` is implemented now**, so a sandboxed application is
refused all of them. Be clear about the scope: this gates clients that connect
through a *sandbox-provided* socket. An ordinary application you launch yourself
is still an ordinary application with your privileges, on this and on every other
Wayland compositor. What it gives you is that a sandbox can now actually contain
something, which previously it could not.

## A CUDA context could take a display down for a day

The primary 2560×1440 display spent a day scanning out a frozen console, its
connector reading `disconnected` behind a 0-byte EDID. It was not the cable, not
the monitor, and not that night's resume — that suspend was clean.

The damage came from the previous afternoon. A process holding a CUDA context
exited inside `nvidia_uvm`'s teardown, where it cannot be frozen; the freezer
gave up after 20 seconds and the suspend aborted half-done. Suspend now releases
GPU contexts before the freezer runs.

## An unauthenticated model API, reachable from the network

Auditing the LAN-facing AI ports turned up a guard that did not guard. The
firewall unit was wired with `Wants=`, which orders startup but does not gate it,
so any failure of that guard — a bad ruleset, a renamed file, an `nft` upgrade —
left ollama starting anyway and binding `0.0.0.0:11434` with nothing in front of
it. That is an unauthenticated model API on your subnet, and `POST /api/pull` and
`DELETE /api/delete` need no credentials either. It is `Requires=` now, so the
port cannot open unless the rules that fence it off loaded first.

## Install what you'll actually use

`dolphin` (all of Qt6 and KF6) and `wine` + `wine-mono` sat in the base install
line, so **every** install paid for the two largest optional dependency trees —
including Minimal, which exists precisely for the small-disk, headless and VM
cases that want neither. Both are now choices: Full takes them, Minimal takes
neither, Custom asks, and Standard is unchanged.

Declining the file manager used to break things quietly, so that is fixed in the
same breath: the bar's Files button, the desktop's right-click entry and the ISO
mounter's open-the-mount step all went through a hardcoded `dolphin` and simply
did nothing when it was absent — no window, no error, no log line. All three now
go through one helper that honours `$SYNUI_FILE_MANAGER`, falls back to
`xdg-open` only once a handler for directories is actually registered, and says
something when it cannot.

## Also in this release

- **Tray icon menus open under their icon.** They had been landing offset to one
  side or the other, by an amount that differed per icon and changed whenever an
  application added or removed one.
- **The Firefox glass theme reached every profile.** A profile whose directory
  name contains a space was split in two, so it never received the theme, turning
  it off never reverted its preferences, and stray directories were left behind
  wherever the command happened to run from.
- **A short `connect()` could leak kernel stack memory** into the event feed.
  Fixed, along with the `AI_CTX` syscall family being removed outright — it was
  unused surface on the kernel's syscall boundary.
- The kernel module records process identity in the **initial** namespaces, so a
  container cannot present a misleading uid or pid to the detector.
- Scheduling hints are released when their process exits, rather than
  accumulating for the life of the machine.
- A ring-index fix for counter wrap, which turned event counters negative after
  roughly 200 days of uptime.
- `synapd` survives a kernel module reload instead of needing a restart after one.
- The two daemon parsers now run under AddressSanitizer and UndefinedBehaviorSanitizer in CI.
