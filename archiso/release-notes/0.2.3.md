The release that makes SynapseOS updatable at all, plus the sleep and wake
cycle finally working the way it always claimed to. Most of what follows was
broken silently — nothing errored, nothing logged, and there was no way to tell
from the outside.

## An installed SynapseOS could never update. Now it can

Every system installed before this release was frozen at whatever ISO installed
it, and nothing said so.

`syn-install` gave each one a package repository pointing at
`/var/cache/synapseos` — a directory copied off the ISO at install time that
**nothing ever wrote to again**. So `sudo pacman -Syu` faithfully upgraded all
of Arch, reported success, and could never see a newer `synui`, `synapd` or
`synguard`. No error, no warning, no hint. A machine could sit hundreds of
compositor releases behind while looking perfectly up to date.

**`syn-update` closes it.** It fetches the project's source, compares each
component against what is actually installed, shows you the commits in between,
rebuilds what moved and installs it — then republishes into the local repository
so pacman's own view stays honest and a later upgrade cannot offer to put back
what you just installed.

```bash
syn-update check     # read-only: what would change
syn-update apply     # rebuild the changed components and install them
syn-update status    # source revision and installed versions
```

There is a GUI too — **SynapseOS Updates** in the start menu. Note that this is
*not* the same entry as **Update System**, which upgrades Arch. You need both;
they cover different halves of the machine.

Because components are rebuilt from source, this needs `base-devel` — about 17
packages on a system that has none of them. Components with a large prebuilt
payload (`synapse-llama`, `linux-wallpaperengine`, `chibi`) are **not** updated
this way, and `syn-update` says so rather than skipping them in silence; those
move with an ISO upgrade. Full details in the
[Updating](https://github.com/velle999/SYNAPSE/wiki/Updating) wiki page.

## Sleeping and waking

**The machine did not actually go to sleep when told to.** It sat awake with its
monitors dark — sometimes for a minute, in the worst observed case for hours —
and `PM: suspend entry` in the log was not evidence that it had slept.

The cause took measurement to pin down, because the usual tool exonerates the
guilty party. With `NVreg_PreserveVideoMemoryAllocations=1` the NVIDIA driver
copies every resident byte of video memory to disk *from inside its suspend
notifier*, before the kernel freezes anything — and the kernel's own
`pm_print_times` only times device callbacks, so it showed an empty table and
made the driver look innocent.

An A/B with the AI daemon stopped settled it: video memory in use fell by
~4.6 GiB and bytes written fell by ~4.1 GiB, near 1:1, and the stall dropped 57%.
The model on the GPU was the single largest allocation, so **`synapd` now
releases it over a suspend** and reloads on the way back. The stall went from 83
seconds to 17.

**The screen stayed black after a wake** until you typed or moved the mouse, so
there was no way to know the machine was ready — not even the lock screen was
visible. Nothing un-blanked on resume: the only thing that had ever re-enabled
the outputs was an input event. Displays now light up from the resume handler
itself.

**Resume could leave the whole desktop blank with the compositor still running.**
`synui` was alive and drawing nothing — its main thread blocked forever on a lock
held by a worker stuck talking to a dead X server. Alive-but-dispatching-nothing
is indistinguishable from a lock screen if you are the one looking at it. A hung
X server can no longer stop the compositor.

Sleep timers also gain a **3-hour** rung, and whole hours now render as `1h`,
`2h`, `3h` rather than `120m`, which read like a misconfiguration.

## The live ISO's AI was dead on arrival

The live media shipped a 4.3 GB model and then **mounted an empty filesystem
directly on top of it**. On the ISO, `synapd` came up with no model, `syn status`
reported *"model ✗ not installed"*, and every AI feature was inert — while the
download still carried the full 4.3 GB.

The mount dated from a version where the ISO shipped no model and first boot
downloaded one into RAM. The model has shipped on the media since; nobody noticed
the mount was now sitting on top of it. Installed systems were never affected,
which is exactly why this presented as "the installed system works, the live one
doesn't" — the installer reads around the mount.

## Turning the AI off now turns it off

Setting the AI backend to **off** stopped the daemon and nothing else. Its socket
kept listening, so the next program to connect started it straight back up.
Reported as *"AI mode is off but Chibi flips it on anyway"* — Chibi connects on
its first message, and off quietly undid itself.

Off now stops the socket alongside the service, and stops the LAN bridge as well:
that listener accepts connections from anywhere on the network, so any machine on
it could resurrect the daemon remotely, with nothing locally to explain why it
came back. Off also **checks** now, and reports failure instead of asserting
success when the stop did not hold.

One resurrection path deliberately survives: `synguard`, `synnet` and `synui`
each want `synapd`, so an automatic restart of any of them re-enqueues it. Rare
on healthy hardware, more common in a VM.

## `synsh` no longer sends your account name to the model

The shell put `User: <login account>` into every translation prompt, so the model
addressed whoever the account was named after — on a fresh install, typing
`hello` came back greeting the account's owner by name. That is an identity a
shipped image should never have.

A shell translator has no use for a name. What it can act on is whether the
session is root, which decides whether a command needs `sudo` at all — and that
was never being sent. The prompt now carries the privilege and not the identity.
Opt back in with `set ai_user_name <name>` in `~/.synshrc`; the default is empty.

## Also in this release

- **Windows appearing under a stationary cursor now receive pointer focus.**
  `synui` only re-derived which surface was under the pointer when the pointer
  physically moved, so a window that opened under a still cursor got nothing
  until you nudged the mouse. This bit games in particular: SDL only engages a
  pointer lock once its window holds pointer focus, so it would report the lock
  as successful while never actually requesting one.
- **The updater window could not be reopened once closed** — it exited cleanly
  and drew nothing on every later click.
- The local repository no longer advertises versions older than what is
  installed, which could let a repair install silently downgrade a package.
- NVIDIA's sleep units are no longer masked; a previous release masked them on a
  misreading.
